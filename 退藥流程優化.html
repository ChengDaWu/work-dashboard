01

現行流程：每日批次包藥＋即時首日量

先建立共同背景，讓後續的頻率異動與優化邏輯容易理解。

12:00

藥局自動包藥

自動包住院病人一整天 24 小時所需藥量。

12:00–15:00

配送準備

包藥完成後至送達護理站，中間約有 3 小時差。

約 15:00

送達護理站

護理站取得當批次住院用藥。

假日前

提前多包

若隔日為星期日或假日不包藥，前一日多包一天。

重要：因為 12:00 包藥、約 15:00 才送達，相同頻率在不同修改時間點，可能會得到不同的首日量。
02

首日量：從醫囑生效時間算到下一次實際包藥時間

任何時間新增醫囑，都先走首日量流程，不等待下一次 12:00 批次。

首日量計算依據

  • 依 take_times 設計計算。
  • 起點：醫師新增或修改醫囑的時間。
  • 終點：下一次「實際」包藥時間。
  • 若遇假日不包藥，計算區間延長至下一個實際包藥日。
首日量 = 變更時間 → 下一次實際包藥時間
依 take_times 應給的總次數 × 每次劑量

04

優化核心：同一個變更時間點，同時計算「舊餘量」與「新需求」

這是整個優化方案最重要的概念，也是 Diff 的真正含義。

OLD FREQUENCY

舊頻率首日量計算

從「醫師變更頻率的當下」算到「下一次實際包藥時間」， 依舊頻率 take_times 推算。
代表：這個時間點，舊醫囑理論上應該還留在護理站的餘藥量。
⇄
NEW FREQUENCY

新頻率首日量計算

同樣從「醫師變更頻率的當下」算到「下一次實際包藥時間」， 依新頻率 take_times 推算。
代表：從現在開始，依新醫囑實際應該發給護理站的藥量。
Diff = 新頻率此時應發量 − 舊頻率此時應剩餘量
上一次實際發藥量仍然是原始基準資料，但不直接拿整包藥量相減； 系統要先依舊頻率 take_times 換算成「變更當下應剩餘量」，再與新頻率首日量比較。
> 0

不足 → 補藥

新頻率需要的量較多，差額就是需要補發的量。

= 0

剛好 → 不動作

現場舊餘藥足以直接銜接新頻率，不需要補退藥。

< 0

多餘 → 預扣 / 回收

舊頻率應剩餘量較多，差額就是多餘藥量。

05

現行流程 vs 優化流程

報告最後只需要讓主管看到：優化後的決策邏輯更單純、也更容易自動化。

CURRENT

現行流程

  • 停原醫囑與新增新醫囑分開處理。
  • 原餘藥由護理站人工退藥。
  • 新醫囑重新走首日量即時發藥。
  • 退藥與補藥分屬不同操作路徑。
→
PROPOSED

優化流程

  • 同一變更時間點，同時計算舊餘量與新需求。
  • 以 Diff 直接判斷補藥 / 預扣 / 不動作。
  • 不必依「是否已印藥袋」建立不同判斷分支。
  • 規則單一，較容易自動化，也較容易說明與維護。
一句話總結： 把「原本要人工理解的退藥＋補藥流程」，改成「同一時間點比較新舊首日量差額」的單一系統規則。
